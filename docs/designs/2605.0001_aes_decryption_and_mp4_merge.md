# 2605.0001 AES-128 Decryption and Segment Merge for sondeo

**Date:** 2026-05-31
**Status:** draft
**Author:** EP Lin
**Doc type:** Mini RFC

## TL;DR

Add two missing stages to sondeo's download pipeline: (1) **in-process
AES-128-CBC decryption** of segments when the playlist declares `#EXT-X-KEY`
(`METHOD=AES-128`), using Node's built-in `crypto` — no new runtime dependency;
and (2) **merge** of the decrypted segments, in playlist order, into a single
true **`.mp4`** via **`ffmpeg`** stream-copy. `ffmpeg` becomes a required
prerequisite (already present on the dev machine: v8.1.1). A preflight check
fails fast with install instructions if it is missing. Streams that use fMP4 /
`#EXT-X-MAP` are detected and rejected with a clear message rather than
producing a broken file.

## Problem

sondeo today downloads the playlist, the AES key, and every segment, then writes
them to disk as individual files. Two things are missing for the output to be
usable:

1. **Encrypted segments are never decrypted.** When a playlist carries
   `#EXT-X-KEY` (AES-128), every `.ts` segment on disk is ciphertext. The key is
   downloaded but unused, so the segment files are unplayable garbage.
2. **Segments are never merged.** The user is left with hundreds of `.ts`
   fragments and a rewritten `.m3u8`, not one file. Producing the single `.mp4`
   they actually want requires a separate, manual `ffmpeg` invocation that the
   user has to know and run by hand — and which, for an encrypted stream,
   re-does the key fetching sondeo already did.

Evidence this is the real gap: the `output/` directory contains finished
`.mp4`s, confirming the intended end state is one merged `.mp4` per stream —
produced today by a manual external step rather than by the tool.

## Constraints

- **Decryption stays in-process.** The request is explicit: decrypt each
  segment with the downloaded key + IV _before_ writing — not delegated to
  `ffmpeg`'s own HLS reader. This keeps decryption owned and unit-testable
  (byte-exact), and uses `ffmpeg` purely as a container muxer.
- **`ffmpeg` is the muxer, and a hard prerequisite.** It is present on the dev
  machine (v8.1.1). v1 requires it; there is no native-mux fallback. A missing
  `ffmpeg` is a clear preflight error, not a silent degrade.
- **No new runtime npm dependency.** Decryption uses Node `crypto`; merge uses
  `child_process.spawn('ffmpeg', …)`. Runtime deps stay `commander` /
  `m3u8-parser` / `rxjs`.
- **Node 22** runtime → `crypto.createDecipheriv('aes-128-cbc', …)` and
  `child_process.spawn` are available.
- **Existing architecture is DI + RxJS.** New behavior slots in as injected
  services (like `Downloader`/`Parser`/`Writer`), not as ad-hoc code in
  `wrapper.ts`.
- **Order matters for merge, but the current pipeline destroys it.**
  `wrapper.ts` collects segment URIs into a `Set` and downloads with
  `mergeMap(…, 5)`, so both dedup and concurrency erase playlist order.

## Proposed approach

Two new injected services plus a pipeline restructure.

### New interfaces

```ts
interface Decryptor {
  // AES-128-CBC. iv: explicit from EXT-X-KEY, or derived from sequence index.
  decrypt(data: Uint8Array, key: Uint8Array, iv: Uint8Array): Uint8Array;
}

interface Merger {
  // Spawn-free preflight: is ffmpeg resolvable on PATH?
  ffmpegAvailable(): boolean;
  // Concatenate ordered decrypted segment files into a true .mp4 via ffmpeg.
  merge(orderedSegmentPaths: string[], outPath: string): Observable<void>;
}
```

Both registered in `main.ts` via `injector.set(...)` alongside the existing
three (`Parser`/`Downloader`/`Writer`), and resolved in `Wrapper`'s constructor
via `injector.get(...)`.

### Decryption

- Trigger when a segment carries a `key` with `method === 'AES-128'`. Read the
  key **per segment** (`segment.key`), not only `segments[0].key` — m3u8-parser
  attaches the active `#EXT-X-KEY` to each segment, and v1 assumes a single key
  for the whole playlist (see Out of scope: key rotation).
- **Key**: the 16 bytes downloaded from `key.uri` (already fetched today).
- **IV**: use the explicit IV from `#EXT-X-KEY` when present (`key.iv`, the
  4-element `number[]` m3u8-parser exposes — four 32-bit big-endian words →
  16 bytes). When absent, derive per RFC 8216 §5.2: the segment's media sequence
  number as a 16-byte big-endian integer, where media sequence number =
  `#EXT-X-MEDIA-SEQUENCE` (default 0) + the segment's 0-based index in this
  playlist.
- Decrypt **per segment, after download, before the file is written** so the
  on-disk segment is already cleartext and the merge stage is encryption-
  agnostic.

### Merge (ffmpeg, always a true .mp4)

- **Preflight**: before doing work, verify `ffmpeg` resolves on `PATH`. If not,
  fail with a clear, actionable error (`ffmpeg is required … install via 'brew
install ffmpeg'`). No silent fallback.
- **Concatenate via the ffmpeg concat demuxer.** Write an ordered concat list
  (`file 'seg00000.ts'` …) and run:
  `ffmpeg -f concat -safe 0 -i list.txt -c copy <out>.mp4`. `-c copy` is a
  stream copy — no re-encode, so it's fast and lossless; the demuxer assembles
  the ordered TS fragments into a real MP4 container.
- **Output** is always `<name>.mp4`, a true MP4 that plays everywhere.

### fMP4 / `#EXT-X-MAP` guard

- If the manifest declares `#EXT-X-MAP` (fMP4 init segment) or otherwise
  indicates non-TS fragments, **reject with a clear "fMP4 not supported in v1 —
  decrypt/merge with ffmpeg directly" message** instead of emitting a broken
  file. v1 targets AES-128 single-codec TS VOD (the `output/` corpus).

### Pipeline restructuring (`wrapper.ts`)

1. Download + parse the playlist (unchanged), rewrite image-ext → `.ts`
   (unchanged). Run the fMP4 guard and the `ffmpeg` preflight here, before
   downloading segments, so failures are fast.
2. If a key is declared, **fetch the key first** (it must exist before any
   segment can be decrypted).
3. Build an **ordered** list `{ index, uri }[]` from `manifest.segments`,
   replacing the order-destroying `Set`. v1 keeps every segment in playlist
   order without URI dedup (a VOD playlist can legitimately repeat a URI; see
   Open questions).
4. Download segments with bounded concurrency, **carrying the index through**
   (`mergeMap` over the indexed list, concurrency 5). Decrypt each on arrival if
   a key exists. Write each to a temp segment file named by zero-padded index.
5. **Barrier**: once all segments are written, hand the index-ordered file list
   to `Merger.merge(…, outPath)`.
6. Progress bar reporting is unchanged (per-segment `next`); merge emits a final
   status.

## Alternatives considered

**A. In-process decrypt + native MPEG-TS byte-concat (no ffmpeg).** Zero
external prerequisites; concatenated TS plays in VLC/mpv. **Rejected** because
the output is a TS stream, not a true MP4 container — naming it `.mp4` breaks
strict players (QuickTime, browsers), and the explicit request is a playable
`.mp4`. ffmpeg is already installed here, so the "avoid the prerequisite"
benefit doesn't apply.

**B. Pure-Node TS→MP4 muxer (`mux.js` / hand-rolled).** True `.mp4` with no
`ffmpeg`. **Rejected**: a large dependency or a large amount of
container-muxing code to maintain, justified only when `ffmpeg` can't be
assumed. It can be assumed here.

**C. Delegate decryption to ffmpeg too** (`ffmpeg -allowed_extensions ALL -i
playlist.m3u8 -c copy out.mp4`, letting ffmpeg read `#EXT-X-KEY` and decrypt).
Least code. **Rejected**: contradicts the explicit requirement to decrypt
in-process with the downloaded key, makes decryption untestable in isolation,
and re-fetches the key/segments ffmpeg would need to reach over the network
again.

**D. Decrypt only, leave merge to the user (status quo merge).** Decryption is
the higher-value half. **Rejected** as the whole answer because the request is
end-to-end to a single `.mp4`.

## Trade-offs accepted

We accept a **hard `ffmpeg` prerequisite** (the tool will refuse to run the
merge without it) in exchange for **always producing a correct, universally
playable `.mp4`** and keeping zero new npm dependencies. We are choosing
"requires ffmpeg, output is always a true mp4" over "no prerequisite, output is
a TS stream that some players reject." Given ffmpeg is already present, the cost
is borne mainly by future users on machines without it — mitigated by a clear
preflight error.

## Riskiest assumption

**That `ffmpeg -f concat -c copy` over the decrypted TS fragments yields a valid
MP4 for sondeo's real inputs.** This holds for standard single-variant AES-128
TS VOD. It can break on streams with mid-playlist discontinuities, codec/profile
changes, or fMP4 (`#EXT-X-MAP`) — for which stream-copy concat produces a broken
or rejected file. Mitigation: the fMP4 guard rejects the clearest failure case
up front; v1 scope is explicitly AES-128 single-codec TS VOD. If a target stream
falls outside this, the user is told to run ffmpeg directly rather than handed a
corrupt file.

## Success criteria

- An **encrypted** AES-128 test playlist: each decrypted segment is byte-exact
  vs. a known-good reference (pure-Node decrypt unit test, no ffmpeg).
- IV handling is correct for **both** paths: explicit `IV=` from `#EXT-X-KEY`,
  and sequence-number-derived IV when absent.
- **Merge order** matches playlist order **regardless of download completion
  order** (verified by feeding the merger out-of-order completion).
- A full run on a small AES-128 TS fixture produces a single `.mp4` that
  `ffprobe` reports as a valid MP4 with the expected duration/stream count
  (integration check), and that plays (manual smoke check in mpv on at least one
  real input).
- **Missing `ffmpeg`** → fast, clear preflight error before any segment is
  downloaded; no partial/corrupt output.
- **fMP4 / `#EXT-X-MAP`** input → clear "unsupported in v1" error, no broken
  file.
- A **wrong/short key** → loud decryption error, not a silently corrupt segment.

## Out of scope

- fMP4 / `#EXT-X-MAP` initialization-segment streams (detect-and-reject only).
- Mid-playlist **key rotation** (multiple `#EXT-X-KEY` tags); v1 assumes one key.
- `SAMPLE-AES` / DRM / Widevine (only `METHOD=AES-128`).
- Master-playlist variant selection / bitrate ladders.
- Re-encoding, subtitle/extra-audio muxing, trimming.
- Resume/retry of partial downloads (separate concern).

## Open questions (non-blocking)

- Clean up temp segment files + the rewritten `.m3u8` after a successful merge,
  or keep them? (Lean: write segments to a temp subdir, delete on successful
  merge, keep on failure for debugging.)
- Output filename: derive from the playlist filename (→ `<name>.mp4`), or add a
  `--name` flag? (Lean: derive from playlist name for v1.)
- URI dedup: confirmed dropped for v1 (preserve every segment in order). Revisit
  only if a real input shows spurious duplicate downloads.
