# 2605.0001 Execution Graph: AES-128 Decryption and Segment Merge

**Date:** 2026-05-31
**Status:** ready
**Spec:** [2605.0001](../specs/2605.0001_aes_decryption_and_mp4_merge.md)

## Overview

Build in-process AES-128 decryption and an ffmpeg-based segment→mp4 merge for
sondeo. The work splits into two independent streams — a pure-Node **Decryptor**
(unit-testable, byte-exact) and an ffmpeg **Merger** — that converge in a
**Wrapper** pipeline restructure (ordering, guards, error handling). A
foundation slice stands up the missing test runner (vitest) and the synthetic
AES-128 TS fixtures every other slice consumes.

## Execution Graph

```
SL1 (test infra + synthetic fixtures)
 ├──────────────┬───────────────────────────────┐
 ▼              ▼                                 │
SL2 Decryptor   SL4 Merger.ffmpegAvailable        │
 │ (S2,S11u)     │ (S8 preflight)                  │
 ▼              ▼                                 │
SL3 IV helper   SL5 Merger.merge → mp4            │
 │ (S3)          │ (merge mechanics)               │
 │              │                                 │
 └──────┬───────┴─────────────┐                   │
        ▼                     ▼                   ▼
       SL6 pipeline: ordering + cleartext e2e (S1,S5,S6)
        │
        ▼
       SL8 preflight + guards (S8,S9,S10)        [also needs SL4]
        │
        ▼
       SL7 encrypted e2e (S4,S7)                 [also needs SL3, SL5]
        │
        ▼
       SL9 runtime errors (S11,S12,S13,S14)
```

Waves: **W0** = SL1 · **W1** = SL2, SL4 · **W2** = SL3, SL5 · **W3** = SL6 ·
**W4** = SL8 · **W5** = SL7 · **W6** = SL9.

SL8 (guards) is sequenced **before** SL7 (key-fetch/decrypt): both edit the
`src/wrapper.ts` setup region, and guards must reject early (don't fetch a key
for a `SAMPLE-AES`/fMP4 stream you're about to reject), so they're serial.

## Slices

### SL1: Test infrastructure + synthetic AES-128 TS fixtures

- **Depends on:** none
- **Scenarios:** (foundation — no direct spec scenario; enables S1–S14)
- **Tests:**
  - `[example]` Running `npm test` exits 0 with at least one passing test,
    confirming the vitest + TypeScript wiring is operational. (infrastructure)
  - `[example]` Given the committed encrypted fixture and its known key `K` and
    IV `V`, when the ciphertext bytes are decrypted using AES-128-CBC with `K`
    and `V`, then the output is byte-exact equal to the committed plaintext bytes —
    confirming the fixture generator and committed files are internally consistent.
    (infrastructure)
- **Implementation:**
  - Add `vitest` (dev dep) + a `"test": "vitest run"` script in `package.json`.
    Do **not** use jest. Keep `tsconfig.json` as-is; vitest transpiles TS via
    esbuild.
  - `tests/fixtures/generate.ts` is a **one-shot dev tool, NOT run during
    tests** (libx264 output is not byte-stable across ffmpeg builds, so
    regenerating at test time would silently drift the byte-exact S2/S3
    references). It mints 2–3 tiny valid `.ts` segments (the **plaintext**) with
    a _valid_ lavfi graph — e.g.
    `ffmpeg -f lavfi -i "testsrc=size=160x90:rate=15" -f lavfi -i "sine=frequency=1000" -t 1 -c:v libx264 -c:a aac -f mpegts seg.ts`
    (note: `testsrc` and `sine` are **separate** `-f lavfi -i` inputs, not
    `testsrc/sine`), records each segment's `#EXTINF` duration, then AES-128-CBC
    encrypts each with a known `K` and (a) an explicit IV `V`, and (b) a
    sequence-derived IV. Document the ffmpeg version + a "to regenerate, run
    generate.ts and commit" note in a fixtures `README`.
  - **Commit the fixtures as static files** (the source of truth tests read;
    tests never invoke `generate.ts`): plaintext `.ts` segments, encrypted `.ts`
    variants, `K`/`V`/derived-IV **as hex-text files** (e.g. `key.hex`, `iv.hex`
    — loaded with `Buffer.from(text.trim(), 'hex')`, avoids binary-blob
    ambiguity), a cleartext `.m3u8`, an encrypted `.m3u8`
    (`#EXT-X-KEY:METHOD=AES-128,URI=…[,IV=0x…]`), a fMP4 `.m3u8` (`#EXT-X-MAP`),
    and a `SAMPLE-AES` `.m3u8` for the guard slices. Record the expected
    `ffprobe` stream layout (codec/count) alongside the fixtures for S4/SL5.

### SL2: Decryptor — AES-128-CBC with explicit IV

- **Depends on:** SL1
- **Scenarios:** S2, S11
- **Tests:**
  - `[example]` Given the committed AES-128-CBC ciphertext fixture with known key
    `K` (16 bytes) and IV `V` (16 bytes), when `Decryptor.decrypt(ciphertext, K, V)`
    runs, then the returned bytes are byte-exact equal to the committed plaintext,
    and the output length equals the plaintext length (PKCS#7 padding is stripped,
    not a block-padded length). (S2)
  - `[example]` Given a key buffer of 0, 15, 17, or 32 bytes, when
    `Decryptor.decrypt` is called, then it throws an `Error` synchronously whose
    message identifies the key-length problem; no partial output is returned. (S11)
- **Implementation:** add `Decryptor` interface to
  `src/interfaces/interfaces.ts`; `src/decryptorImpl.ts` using
  `crypto.createDecipheriv('aes-128-cbc', key, iv)`. Pure, no I/O.
  - **PKCS#7 note:** HLS AES-128 is CBC + PKCS#7 (RFC 8216), so Node's default
    `setAutoPadding(true)` is correct for spec-compliant streams and our
    fixtures. Known v1 limitation: a non-PKCS#7-padded real-world segment would
    make Node throw "bad decrypt"; if that surfaces on real input, switch to
    `setAutoPadding(false)` + manual tail handling. Fixture-tested only in v1 —
    leave a code comment noting the assumption.

### SL3: IV derivation helper + decrypt with derived IV

- **Depends on:** SL2
- **Scenarios:** S3
- **Tests:**
  - `[example]` Given a media sequence number `m` and a 0-based segment index
    `i`, the IV derivation helper produces the 16-byte big-endian encoding of
    `m + i`: for `m=7, i=0` → `00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 07`;
    for `m=0, i=258` → `00 00 00 00 00 00 00 00 00 00 00 00 00 00 01 02`; for an
    `m+i` value exceeding `0xFFFFFFFF`, the encoding correctly spans the upper
    bytes (not truncated to 4 bytes). (S3)
  - `[example]` Given an explicit `key.iv` expressed as 4 × 32-bit big-endian
    words (a `number[]`), when the IV helper converts it, then the result is the
    correct 16-byte concatenation of those words in big-endian order. (S3)
  - `[example]` Given a fixture encrypted with a derived IV for a known `m` and
    `i`, when `Decryptor.decrypt` is called with the derived IV, then the output
    is byte-exact equal to the committed plaintext. (S3)
- **Implementation:** widen `src/types/m3u8-parser.d.ts` to expose
  `mediaSequence: number` on `Manifest`; add an `iv-for-segment` helper
  (explicit-vs-derived) near the Decryptor.

### SL4: Merger.ffmpegAvailable() preflight

- **Depends on:** SL1
- **Scenarios:** S8
- **Tests:**
  - `[example]` Given a `PATH` that includes the real system `ffmpeg` binary,
    when `Merger.ffmpegAvailable()` is called, then it returns `true` without
    spawning a process. (S8)
  - `[example]` Given a `PATH` environment stubbed to exclude any `ffmpeg`
    binary, when `Merger.ffmpegAvailable()` is called, then it returns `false`
    without spawning a process. (S8)
- **Implementation:** add `Merger` interface to `src/interfaces/interfaces.ts`;
  `src/mergerImpl.ts` with a spawn-free `ffmpegAvailable()` (PATH/`which`-style
  resolution).

### SL5: Merger.merge() — ffmpeg concat → true .mp4

- **Depends on:** SL4, SL1
- **Scenarios:** S1, S4
- **Tests:** (integration — runs real ffmpeg over the synthetic TS fixtures)
  - `[example]` Given an ordered list of the synthetic plaintext `.ts` fixture
    segments, when `Merger.merge(segments, out.mp4)` completes, then `ffprobe`
    reports the output file as an mp4 container (`format_name` contains `"mp4"`),
    with a stream count and codec matching the fixture's recorded layout, and
    `format.duration` within ±0.5 s of the sum of the fixture's `#EXTINF`
    durations. (S1, S4)
  - `[example]` Given `Merger.merge` is called with an empty segment list or an
    invalid path and ffmpeg exits non-zero, the returned observable emits an error
    rather than completing silently. (S1, S4)
- **Implementation:** `merge()` writes an ordered concat list and spawns
  `ffmpeg -f concat -safe 0 -i list.txt -c copy <out>.mp4`; wrap spawn in the
  returned `Observable<void>`.

### SL6: Pipeline restructure — ordering + cleartext end-to-end

- **Depends on:** SL2, SL5
- **Scenarios:** S1, S5, S6
- **Tests:**
  - `[example]` Given a stub `Downloader` that resolves segments in reverse
    playlist order, and a second case with shuffled completion order, when the
    pipeline reaches the merge barrier, then the path list handed to the fake
    `Merger` is in ascending playlist-index order — not download-completion order.
    (S5)
  - `[example]` Given a playlist where the same segment URI appears K times
    (K ≥ 2), when the pipeline runs, then the `Downloader` is invoked exactly N
    times total (one per playlist entry including duplicates) and the fake `Merger`
    receives exactly N entries in playlist order (no dedup). (S6)
  - `[example]` Given a cleartext fixture playlist whose downloads complete in
    arbitrary order, when a full run completes, then exactly one `.mp4` exists at
    the derived output path, the process exits 0, and `ffprobe` reports it as a
    valid mp4 container with `format.duration` within ±0.5 s of the summed
    `#EXTINF` durations. (S1)
- **Implementation:** replace the `Set` in `src/wrapper.ts` with an ordered
  `{index, uri}[]`; carry `index` through `mergeMap(…, 5)`; write index-named
  temp files; barrier on all-written; call `Merger.merge` in index order. Wire
  `Decryptor`/`Merger` in `src/main.ts`.

### SL7: Encrypted pipeline end-to-end (key-first + per-segment decrypt)

- **Depends on:** SL8, SL3, SL5 (transitively SL6)
- **Scenarios:** S4, S7
- **Tests:**
  - `[example]` Given the committed encrypted AES-128 fixture playlist, when a
    full run completes, then the output `.mp4` passes `ffprobe` validation:
    `format_name` contains `"mp4"`, stream count/codec matches the fixture's
    recorded layout, and `format.duration` is within ±0.5 s of the summed
    `#EXTINF` durations. (S4)
  - `[example]` Given an encrypted playlist that declares `#EXT-X-KEY` once
    (single key for all N segments), when the pipeline runs, then all N segments
    are decrypted without error and the merge barrier is reached with N decrypted
    temp files — confirming per-segment key lookup resolves the single declared
    key for every segment, not just the first. (S7)
- **Implementation:** in `src/wrapper.ts`, fetch `key.uri` bytes before media
  segments; decrypt each downloaded segment (explicit/derived IV via SL3) before
  writing its temp file.

### SL8: Preflight + manifest guards (fail before any download)

- **Depends on:** SL6, SL4
- **Scenarios:** S8, S9, S10
- **Tests:**
  - `[example]` Given `Merger.ffmpegAvailable()` returns `false`, when a run
    starts, then it fails with an error message that names `ffmpeg` and includes
    an install hint, the `Downloader` is invoked zero times, the process exits
    non-zero, and no `.mp4` exists at the derived output path. (S8)
  - `[example]` Given a manifest that declares `#EXT-X-MAP` (fMP4 init segment),
    when a run starts, then it fails before any segment download (zero `Downloader`
    invocations) with an error message indicating fMP4 is unsupported, exits
    non-zero, and no output file or partial output exists. (S9)
  - `[example]` Given a manifest with `#EXT-X-KEY` whose `METHOD` is `SAMPLE-AES`
    (or any value other than `AES-128`), when a run starts, then it fails before
    any segment download (zero `Downloader` invocations) with an error message
    naming the unsupported method, exits non-zero, and no `.mp4` is produced. (S10)
- **Implementation:** add the preflight + guard checks at the top of the
  `src/wrapper.ts` pipeline, before segment fan-out.

### SL9: Runtime error handling

- **Depends on:** SL6, SL7
- **Scenarios:** S11, S12, S13, S14
- **Tests:**
  - `[example]` Given a playlist with zero media segments, when a run starts,
    then `Merger.merge` is never called, a clear "no segments" error is surfaced,
    and the process exits non-zero. (S12)
  - `[example]` Given an encrypted playlist whose key fetch fails (the key URI
    download rejects), when a run starts, then it fails before any media-segment
    download request is issued (zero media `Downloader` invocations), surfaces an
    error indicating the key could not be fetched, exits non-zero, and writes no
    `.mp4`. (S13)
  - `[example]` Given a run where one media segment download fails after others
    have succeeded, when that failure occurs, then the pipeline aborts on first
    failure, `Merger.merge` is never invoked with a partial file list, an error
    identifying the segment download failure is surfaced, and the process exits
    non-zero with no `.mp4` written. (S14)
  - `[example]` Given a run where one segment's decryption throws an error (e.g.
    the key is wrong for that segment), then the run surfaces the decryption error,
    exits non-zero, and no decrypted temp file for the failing segment is left on
    disk. (S11)
- **Implementation:** error propagation in `src/wrapper.ts` (empty-guard,
  key-fetch error, segment-error abort, decrypt-error surfacing); ensure temp
  cleanup on the failing path.

## Parallelization

- **W0:** SL1 alone (everything depends on it).
- **W1:** SL2 ‖ SL4 (Decryptor stream vs Merger stream — both add an interface to
  `src/interfaces/interfaces.ts`; if run concurrently, serialize that one file
  edit or write both interfaces in a single pass).
- **W2:** SL3 ‖ SL5.
- **W3:** SL6 (convergence point — needs both streams).
- **W4:** SL8 (guards — added to the SL6 wrapper setup region).
- **W5:** SL7 (encrypted path — key-fetch + per-segment decrypt, after guards).
- **W6:** SL9.

SL8 → SL7 are **serial, not parallel**: both edit `src/wrapper.ts`'s setup
region, and guards must reject before key-fetch.

Streams A (SL2→SL3) and B (SL4→SL5) are fully independent and the biggest
parallelism win.
