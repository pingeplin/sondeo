# 2605.0001 AES-128 Decryption and Segment Merge

**Date:** 2026-05-31
**Status:** draft
**Author:** EP Lin
**Design doc:** [2605.0001](../../docs/designs/2605.0001_aes_decryption_and_mp4_merge.md)

## Context

`sondeo` downloads an HLS playlist and its `.ts` segments to disk via an RxJS
pipeline in `src/wrapper.ts`. It already fetches the AES key referenced by
`#EXT-X-KEY` but never uses it, and it never combines segments. The result is a
directory of individual segments — ciphertext when the stream is encrypted —
plus a rewritten `.m3u8`, never a single playable file. The existing pieces are
injected services behind interfaces in `src/interfaces/interfaces.ts`
(`Downloader`, `Parser`, `Writer`), wired in `src/main.ts`.

The project currently has **no test runner** (only `npm run build` via webpack);
implementation will need to add one (a `/plan` concern).

## Motivation

The intended end state is one playable `.mp4` per stream (the `output/`
directory confirms this), produced today by a manual, error-prone external
`ffmpeg` step that also can't reuse the key sondeo already downloaded. Building
decryption and merge into the tool makes it self-contained and correct for its
actual inputs (AES-128 single-codec TS VOD).

## Proposed Solution

### Overview

Add two injected services — a **`Decryptor`** (in-process AES-128-CBC via Node
`crypto`) and a **`Merger`** (concatenate decrypted segments into a true `.mp4`
via `ffmpeg`) — and reorder the `wrapper.ts` pipeline so segments are tracked in
playlist order, decrypted on arrival, and merged after all are downloaded.

### Key Components

- **`Decryptor`** (`src/decryptorImpl.ts`) — `decrypt(data, key, iv)` returns
  AES-128-CBC plaintext. Pure Node `crypto`; no I/O. Throws on an invalid key
  length or undecryptable input.
- **`Merger`** (`src/mergerImpl.ts`) — `merge(orderedSegmentPaths, outPath)`
  spawns `ffmpeg` with the concat demuxer and `-c copy` to write a true `.mp4`.
  Exposes a preflight that verifies `ffmpeg` is resolvable on `PATH`.
- **`Wrapper`** (`src/wrapper.ts`, modified) — runs guards/preflight up front,
  fetches the key first, downloads segments with bounded concurrency while
  preserving playlist index, decrypts each on arrival, writes index-named temp
  files, then merges in index order.
- **IV helper** — explicit IV from `key.iv` (4 × 32-bit big-endian words → 16
  bytes), else the segment's media sequence number (`#EXT-X-MEDIA-SEQUENCE`
  default 0 + 0-based index) as a 16-byte big-endian integer. The base
  sequence is read from `manifest.mediaSequence` (m3u8-parser emits it); the
  hand-written `src/types/m3u8-parser.d.ts` must be widened to expose
  `mediaSequence: number` on `Manifest`, since it omits it today.

### Data Flow

1. Download + parse the playlist; rewrite image extensions → `.ts` (unchanged).
2. **Preflight + guards** (before any segment download): reject if `ffmpeg` is
   not on `PATH`; reject if the manifest declares `#EXT-X-MAP` / fMP4; reject if
   an encryption `method` other than `AES-128` is present.
3. If a key is declared, fetch the key bytes first.
4. Build an ordered `{ index, uri }[]` from `manifest.segments` (no URI dedup;
   playlist order preserved).
5. Download segments with `mergeMap(…, 5)`, carrying `index` through. Decrypt
   each on arrival when a key exists. Write to a temp file named by zero-padded
   `index`.
6. After all segments are written (barrier), pass the index-ordered file list to
   `Merger.merge(files, outPath)` → `<name>.mp4`.

### API / Interface Changes

```ts
interface Decryptor {
  decrypt(data: Uint8Array, key: Uint8Array, iv: Uint8Array): Uint8Array;
}

interface Merger {
  ffmpegAvailable(): boolean;
  merge(orderedSegmentPaths: string[], outPath: string): Observable<void>;
}
```

No CLI flag changes for v1 (output name derived from the playlist filename).

## Alternatives Considered

See the design doc for the full argument. In brief: native TS byte-concat (no
ffmpeg) was rejected because a TS-in-`.mp4` file breaks strict players; a
pure-Node TS→MP4 muxer was rejected as disproportionate; delegating decryption
to ffmpeg was rejected because in-process decryption is an explicit requirement
and keeps decryption unit-testable.

## Security Considerations

- Key material is held in memory only for the duration of a run; it is written
  to disk only as the (transient) downloaded key file already produced today.
- An invalid key length or wrong key must fail loudly rather than silently
  emitting a corrupt segment, so a bad input can't be mistaken for success.

## Acceptance Scenarios

### Happy Path

- **S1:** Given a cleartext playlist (no `#EXT-X-KEY`) of N segments whose
  downloads complete in arbitrary order, when sondeo runs, then exactly one
  output `.mp4` is produced at the derived `<name>.mp4` path, the process exits
  zero, and `ffprobe` reports it as a valid MP4 container whose duration equals
  the sum of the playlist's `#EXTINF` durations (± container rounding, see S4 for
  the tolerance). (Byte-level segment ordering is asserted separately in S5 via
  the merger's input list; the `.mp4` is a remuxed container, so its bytes are
  not a raw concatenation of the TS segments.)
- **S2:** Given a fixture built by AES-128-CBC encrypting a known plaintext `P`
  with a known 16-byte key `K` and a known 16-byte IV `V` (the fixture is
  generated once, e.g. via `crypto.createCipheriv('aes-128-cbc', K, V)` with
  PKCS#7 padding, and committed alongside `K`, `V`, and `P`), when
  `Decryptor.decrypt(ciphertext, K, V)` runs, then the returned bytes are
  byte-exact equal to `P` (asserted with `Buffer.equals` / deep byte
  comparison), including correct PKCS#7 unpadding so the output length equals
  `P.length`, not a block-padded length.
- **S3:** Given the IV-derivation path (no explicit `IV=` on `#EXT-X-KEY`), for a
  segment at 0-based index `i` with `#EXT-X-MEDIA-SEQUENCE = m`: (a) the IV helper
  produces the 16-byte big-endian encoding of `(m + i)` — e.g. `m=7, i=0` →
  `00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 07`; `m=0, i=258` →
  `… 00 00 01 02` — verifiable directly against expected byte arrays; and (b)
  given a fixture encrypted with that exact derived IV and key `K`, when
  `Decryptor.decrypt` runs with the derived IV, then the output is byte-exact
  equal to the known plaintext `P`. Cover at least one `m=0` case and one
  `m+i > 0xFFFFFFFF` case to confirm the encoding spans the full 16 bytes, not
  just the low 4.
- **S4:** Given the committed encrypted AES-128 TS fixture playlist (whose
  expected stream layout is recorded with the fixture — e.g. exactly one H.264
  video stream, or one video + one AAC audio stream, as the fixture declares),
  when sondeo completes, then running `ffprobe -v error -show_format
-show_streams` (parsed as JSON) on the output `.mp4` reports: `format_name`
  containing `mp4`, exit code 0 (no decode errors on stderr), a stream set
  matching the fixture's recorded codec/count, and `format.duration` within
  ±0.5 s of the sum of the playlist's `#EXTINF` durations. (Tolerance is ±0.5 s
  to absorb container-edit-list/timestamp rounding; tighten if the fixture proves
  it stable.)

### Edge Cases

- **S5:** Given an N-segment playlist whose segment downloads complete in
  reverse (and, in a second case, shuffled) order — forced via a stub
  `Downloader` that resolves each segment after a controlled delay — when the
  pipeline reaches the merge barrier, then the `orderedSegmentPaths` array passed
  to `Merger.merge` is in ascending playlist-index order (`seg00000…seg0000N-1`),
  not download-completion order. (Asserted at the `Merger` interface boundary
  with a spy/fake, since segment order cannot be recovered from the remuxed
  `.mp4`. The fake `Merger` records its first argument; merge order is the array
  order.)
- **S6:** Given a playlist of N entries that lists the same segment URI K times
  (K ≥ 2), when sondeo runs, then (a) the `Downloader` is invoked N times total
  (once per playlist entry, including each repeat — asserted via a spy on the
  `Downloader`), and (b) the `orderedSegmentPaths` array handed to `Merger.merge`
  has length N with one entry per playlist position in playlist order (no dedup,
  asserted at the `Merger` boundary as in S5).
- **S7:** Given an encrypted playlist that declares `#EXT-X-KEY` once (single key
  for all segments), with all N segments encrypted under that one key, when
  sondeo runs, then all N segments decrypt successfully (no decryption error is
  raised for any segment) and the run reaches the merge barrier with N decrypted
  temp files — i.e. the per-segment key lookup resolves the playlist's single
  active key for every segment, not just the first.
- **S12:** Given a playlist with zero media segments (`manifest.segments` is
  empty), when sondeo runs, then it does not invoke `Merger.merge` with an empty
  list and does not produce a zero-byte/invalid `.mp4`; instead it surfaces a
  clear "no segments to merge" error and **exits non-zero** (a zero-segment
  playlist is a hard error, consistent with the current `wrapper.ts` throw on
  empty segments).

### Error Scenarios

- **S8:** Given `Merger.ffmpegAvailable()` returns `false` (ffmpeg not resolvable
  on `PATH`), when sondeo starts a run, then it fails fast with an actionable
  error whose message names `ffmpeg` and includes an install hint (e.g. `brew
install ffmpeg`), the `Downloader` is invoked **zero** times (no segment is
  downloaded — asserted via a `Downloader` spy), the process exits non-zero, and
  no `.mp4` output file exists at the derived path.
- **S9:** Given a manifest that declares `#EXT-X-MAP` (fMP4 init segment), when
  sondeo runs, then it rejects before downloading any segment (the `Downloader`
  is invoked zero times) with an error whose message indicates fMP4 is
  unsupported in v1, exits non-zero, and no `.mp4` (and no partial output) exists
  at the derived path.
- **S10:** Given an `#EXT-X-KEY` with a `method` other than `AES-128` (case:
  `SAMPLE-AES`), when sondeo runs, then it rejects before downloading any segment
  (the `Downloader` is invoked zero times) with an error whose message indicates
  the encryption method is unsupported and names the offending method, exits
  non-zero, and no `.mp4` exists at the derived path.
- **S11:** When `Decryptor.decrypt` is called with a key that is not exactly 16
  bytes (cases: 0, 15, 17, and 32 bytes), then it throws an `Error` whose message
  identifies the key-length problem (the call throws synchronously; it does not
  return partial/empty output). Additionally, given a full run where one
  segment's decryption throws (e.g. wrong key for that segment), then the run
  surfaces the error and exits non-zero, and no decrypted temp file is left on
  disk for the failing segment.
- **S13:** Given an encrypted playlist whose key fetch fails (the `Downloader`
  rejects/errors on `key.uri`), when sondeo runs, then it fails before
  downloading any media segment (key is fetched first per the data flow; the
  `Downloader` receives zero media-segment requests), surfaces an error
  indicating the key could not be fetched, exits non-zero, and writes no `.mp4`.
- **S14:** Given a run where a **media segment** download fails (the `Downloader`
  errors on a segment URI after others have succeeded), when sondeo runs, then it
  **aborts on that first failure** (no retry — retry/resume is out of scope per
  Trade-offs), does **not** invoke `Merger.merge` with a partial/short file list,
  surfaces an error identifying segment download failure, exits non-zero, and
  writes no `.mp4`.

## Trade-offs and Limitations

- **Hard `ffmpeg` prerequisite** — the merge refuses to run without `ffmpeg` on
  `PATH`; no native-mux fallback in v1.
- **Scope is AES-128 single-codec TS VOD** — fMP4, mid-playlist key rotation,
  `SAMPLE-AES`/DRM, master-playlist variant selection, re-encoding, and
  download resume are out of scope and (where detectable) rejected rather than
  mishandled.
- `ffmpeg -c copy` concat assumes consistent codecs/timestamps across segments;
  discontinuities may still yield imperfect timing (acceptable for v1 VOD).

## Open Questions

- [ ] Clean up temp segment files + the rewritten `.m3u8` on successful merge,
      or retain them? (Lean: temp subdir, delete on success, keep on failure.)
- [ ] Output filename: derive from playlist name (lean) vs. add a `--name` flag.

**Resolved during spec review:**

- Zero-segment playlist (S12) → hard error, non-zero exit (matches existing
  `wrapper.ts` behavior).
- Segment-download failure (S14) → abort on first unrecoverable failure, no
  retry (retry/resume out of scope).
- `Merger` preflight → a distinct, spawn-free `ffmpegAvailable(): boolean`
  method (design doc interface updated to match).
- `#EXT-X-MEDIA-SEQUENCE` → read from `manifest.mediaSequence`; widen the
  hand-written `m3u8-parser.d.ts` to expose it (a `/plan` task).
